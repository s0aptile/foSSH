### §3.8 — Data-at-rest encryption

Scoped to the spool specifically, not the rollup SQLite database — see ADR-0027 for the full reasoning (the database holds k-anonymity-folded aggregates; the spool is where genuinely raw, per-visitor telemetry actually sits on disk, even if briefly). Built: `fossh_admin::data_key` (per-install key, race-safe `load_or_generate`, 5 tests including 8 real concurrent threads racing a cold-start), `fossh_ingest::crypto` (ChaCha20-Poly1305 seal/open, 7 tests covering the round trip, wrong key, tampered ciphertext, and truncation), and wiring through all three transports that touch the spool: `fossh-cgi` (loads the key once per process, after the privilege drop, before the `/healthz` fast path would ever need it), `fossh-cli maintain`, and `fossh-ffi`'s `mode = "spool"` path (`record`/`fossh_flush`) — confirmed by running `fossh-ffi`'s own `flush_drains_the_spool_in_spool_mode` test, which exercises the modified code directly, not just a unit test of the crypto primitive in isolation.

Added two integration-level tests beyond the crypto module's own unit tests: one asserts the literal on-disk spool file bytes don't contain a distinctive plaintext path/name marker (proving encryption actually happens at the file level, not just in a round-trip assertion that could pass even if encryption were accidentally a no-op), and one confirms draining with the wrong key reports every frame `Corrupt` rather than panicking or silently producing wrong data.

Full workspace (both the root and `fossh-ffi`'s separate one) still green after the change: 280 + 32 = 312 tests, clippy clean, fmt clean in both. The RPM built for §3.11 predates this change — rebuilding it to pick up the new code is a follow-up, not done as part of this entry.

### §3.1 — glibc gatekeeping

Built: `fossh_core::glibc_gate` (pure `ldd --version` parsing/comparison, 7 tests), `fossh_cli::common::detect_glibc_version` (the one I/O-performing caller both `doctor` and the new `fossh glibc-check` subcommand share), and the floor constant (2.17, per §2.5's candidate). Deliberately not wired into `fossh-cgi`'s per-request path — see ADR-0024 for the full reasoning (subprocess-per-request would tax the sub-5ms p99 budget for no benefit, since the host's glibc can't change request-to-request).

Adversarial pass caught one real, moderate-to-high-severity bug: neither call site checked `ldd`'s exit status before trusting its stdout, so a failing `ldd` (e.g. a half-broken glibc install — precisely the failure mode this check exists to catch) that still printed something version-shaped on stdout parsed as a clean pass. Confirmed empirically against the compiled binary with a shadowed fake `ldd` on `$PATH`, not just by reading the code. Fixed by collapsing both call sites onto one shared helper that checks `status.success()` first — see ADR-0024. Re-ran the adversarial repro against the fix directly; it now correctly refuses.

Also caught and fixed: a doc comment in `glibc_gate.rs` referenced an ADR that didn't exist yet (fixed by writing ADR-0024 for real, not by softening the comment) and a dangling `RULES.md` pointer in the refusal message (RULES.md has no glibc content). That refusal message no longer points anywhere at all as of the `dev/` reorg below — see that entry for why.

No deviation from §2.5's locked decision. One thing worth being explicit about, flagged in ADR-0024 too: the check exists but isn't automatically invoked by anything yet — that lands with §3.2's systemd unit (`ExecStartPre=`).

### §3.2 — Native CGI hardening

Built: privilege-drop (`fossh-cgi/src/privdrop.rs`, using `nix`'s safe wrappers, never touching this crate's `#![forbid(unsafe_code)]` — setgid → initgroups → setuid, then verifies the drop actually stuck by attempting to reclaim root); the SELinux module (`packaging/selinux/fossh.{te,fc}`, written from scratch in raw native TE syntax since this environment has `checkmodule`/`semodule_package` but not `selinux-policy-devel`'s M4 interface library — see the file's own header comment); and the systemd units (`packaging/systemd/fossh-fcgiwrap.{socket,service}`, `fossh.tmpfiles.conf`) with the full hardening directive set (`PrivateNetwork`, `ProtectSystem=strict`, `NoNewPrivileges`, capability/syscall restriction, etc.) plus `ExecStartPre=fossh glibc-check`.

Verified as far as this rootless environment allows: `checkmodule`/`semodule_package` both compile and package the policy module cleanly (real compile, re-run against the final file content, not just written-and-hoped); `systemd-analyze verify` parses both units cleanly (only complaining that `/usr/bin/fossh`/`/usr/sbin/fcgiwrap` aren't installed system-wide here, which is expected pre-install). - **Missing ancestor-directory `search` grants** for `/etc` (`etc_t`), `/usr` (`usr_t`), `/var` (`var_t`), `/var/lib` (`var_lib_t`) — SELinux checks `dir:search` at every path component, so without these the dynamic linker likely can't even resolve `libc`/`ld.so.cache` and the domain can't reach its own data directory. Likely would have broken every single exec. **Fixed**: added explicit `search`/`read`/`getattr` grants for all four, plus `lib_t:dir` (the directory form of a type this module already required, previously only granted `file`/`lnk_file` access on).
- **`/dev/urandom` (`urandom_device_t`) never granted at all** — confirmed via `fossh-ingest/src/random.rs` that this is opened directly (not `getrandom(2)`) on the hot path whenever the daily salt rotates. **Fixed**: added `chr_file { read write getattr open ioctl }` on `urandom_device_t`.
- **`capability { setuid setgid }` was `require`d but never actually `allow`ed** — would have blocked `privdrop.rs` under enforcement in the one scenario it exists for (this binary genuinely exec'd as root). **Fixed**: added `allow fossh_cgi_t self:capability { setuid setgid };`.

Also addressed, not a bug but a real architectural gap the reviewer flagged and I couldn't resolve without root: the shipped systemd unit execs `fcgiwrap`, not `fossh-cgi`, directly — `fcgiwrap` itself execs `fossh-cgi` per request, and whatever domain `fcgiwrap` actually runs in (the unit sets no `SELinuxContext=`) might not be `init_t` or `httpd_t` at all; Fedora commonly lands such units in `unconfined_service_t`, in which case the transition never fires and `fossh-cgi` runs completely unconfined, silently. Added `unconfined_service_t` as a third source domain for the same transition, as a defensive best guess — but the actual answer (`ps -eZ | grep fcgiwrap` after a real `semodule -i` + service start) is still open and needs root to confirm; tracked here rather than glossed over.

While fixing the above, also trimmed genuinely unused permissions the reviewer traced through the actual ingest code (`lock`/`map` on `fossh_data_t`/`fossh_var_run_t:file` — nothing on this path uses `mmap()` or advisory locking, per ADR-0013), removed redundant `entrypoint`/`execute_no_trans` grants on the source domains' view of the executable (the check only consults the target domain's relationship, already granted separately), and corrected a stale comment claiming `fossh_data_t` represents the SQLite database — it doesn't; `fossh-cgi` never opens `fossh.db` directly, only the JSON site-cache and per-site spool/ratelimit/nonce files. ### §3.9 — Local TUI admin console — QA gate closed out retroactively

`crates/fossh-tui` (dashboard, real telemetry-summary screen, §2.6/§3.11 setup wizard) was implemented and committed (`8f71713`) in an earlier entry in this same chapter, but — unlike every other sub-chapter above — never actually went through this project's own mandatory sequence: implement → adversarial review → fix → retrospective → this table updated. It sat at "not started" in the status table the whole time despite being real, tested, committed code. Caught only by chance, re-reading this file end to end during the directory reorg above. Ran the missing review now, independently, rather than just correcting the table entry cosmetically.

**Adversarial review findings, all independently verified (build/test/clippy re-run, not assumed) and fixed:**

1. **High severity — verifying a pre-existing token file could never succeed.** `Wizard::new` set `pending_hash: None` unconditionally regardless of whether a token file already existed, and only `generate()` (reachable only from `NoTokenFound`) ever populated it. So reopening the TUI between generating a token and verifying it — exactly the shape this becomes once §3.3's watchdog exists and always writes the file in a separate process from this one — left `submit()` permanently unable to succeed, no matter what was typed, with no in-app recovery path. The existing test suite didn't catch it: `existing_token_file_starts_at_awaiting_input` asserted only the starting `Step`, never attempted a full verify. Fixed by having `Wizard::new` read the file and re-derive the hash itself (new `fossh_admin::setup_token::hash_of`, the same primitive `generate()` already uses internally) rather than assuming a hash it never had. Regression tests added: a full generate-elsewhere-then-verify-here cycle, plus a wrong-input-against-a-recovered-hash case.
2. **Zeroization gap, real but defense-in-depth rather than actively exploitable.** The setup token's plaintext — both the freshly-generated copy (`Step::TokenJustGenerated`) and whatever the operator types while verifying (`Wizard::input`) — lived in plain, unzeroized `String`s. A wrong guess only reset length (`String::clear()` doesn't touch the underlying bytes), and a *correct* guess never cleared the buffer at all. Worth fixing for consistency with this project's own bar elsewhere (`fossh-admin::data_key`'s `Zeroizing` usage) even though the token is already burned/invalidated by the time this matters, so there's no live credential left to steal this way — the actual exposure needs something else to go wrong first (a core dump, a ptrace read, a swapped page). One sharp edge the review caught that a bare `Zeroizing<String>` alone wouldn't have closed: the workspace's release profile sets `panic = "abort"`, which skips unwinding, so a `Drop` impl doesn't fire if the process panics while the plaintext is still live — the actual fix has to be *proactive* clearing the moment the value is no longer needed, not just wrapping it and trusting a clean shutdown. Fixed: both fields are now `Zeroizing<String>`, and `Wizard` explicitly zeroizes `input` right after a wrong guess, right after a successful verify, and on cancel (see next finding) — not left to whenever the struct eventually drops. Also fixed the render path in `ui.rs`, which had been `plaintext.clone()`-ing the generated token into a fresh, unprotected `String` on every single frame redraw (the event loop redraws roughly every 100ms while that screen is shown) purely to display it — switched to borrowing (`.as_str()`) instead, so rendering no longer keeps minting new unprotected copies of a live secret for as long as the screen stays up.
3. **The status line was actively lying, and there was no way to cancel out of token entry short of quitting the whole app.** The footer unconditionally advertised "q quit · 1/2/3 switch screen · r refresh" on every screen — but the raw-input-capture state (`Step::AwaitingInput`) routes every key, including q/1/2/3, into the token buffer instead, so none of those claims were true while actually typing a token. The only key that still did something in that state was Esc — and it quit the entire application, not just the wizard, with no mention of Esc in the footer at all and no other way back to a menu. Fixed: the footer is now context-sensitive (different, accurate hints per screen and per wizard step), and Esc during token entry now clears the input and returns to the dashboard instead of quitting.
4. **`FOSSH_K_ANONYMITY=0` silently defeated k-anonymity on this screen's own telemetry display.** The env var was parsed straight into `u32` with no floor check, so an explicit `0` sailed through — and `fossh-store`'s k-anonymity fold is `if uniques < k_anonymity`, meaning `k=0` folds nothing into `(other)` ever, directly contradicting the Telemetry screen's own "k-anonymized" label. `fossh-cli`'s `doctor` already names exactly this as a real invariant to check (`k_anonymity >= 1`); this TUI's own intake path had no equivalent. Fixed with the same floor.
5. **Trivial, fixed anyway:** `fossh-tui` had no `#![forbid(unsafe_code)]` despite containing zero `unsafe` — every other crate in this project has it; added for consistency. `data.rs`'s `start_of_today` used `%`, which overshoots the day boundary for a negative timestamp (`rem_euclid` doesn't) — unreachable today since its only caller's fallback is exactly `0`, fixed anyway since the fix is free and the function isn't `pub` so nothing enforces non-negativity at its own boundary.
6. **Acknowledged, deliberately not fixed:** a site slug containing wide/multi-byte Unicode characters will misalign the Telemetry screen's fixed-width columns (Rust's `{:<N}` pads by `chars().count()`, not display width). Confirmed this cannot panic — cosmetic only. Not worth a `unicode-width`-aware padding routine for what is, in practice, an ASCII-slug table; narrow enough not to be worth the complexity, same call as the SELinux reclaim-check nit in §3.2's retrospective.

**Verification:** 18 tests in `fossh-tui` now (up from 8) plus 1 new test in `fossh-admin` (`hash_of` round-trips against `generate()`'s own hash) — every fix above has a regression test, including a new `app.rs` test module that didn't exist before this pass (`esc_during_token_entry_cancels_back_to_dashboard_instead_of_quitting`, `nav_and_quit_keys_are_captured_as_token_text_during_input`, plus two nav sanity checks). `cargo clippy -- -D warnings` and `cargo fmt --check` clean. Full workspace re-run clean after all of it: root 291 tests (was 280), `fossh-ffi` 32 tests, 0 failures. Rendered every screen through `ratatui::backend::TestBackend` at two terminal sizes (100×30 and a narrow 60×20) via a temporary test, confirmed no clipping under the new padding/rounded-border treatment and that the context-sensitive footer actually shows the right hint per screen/step, then removed the temporary test — the same "write it, verify, revert cleanly" discipline the adversarial-review pass itself used for the pre-existing-file repro.

Also folded in, same pass, per a separate direct request ("tui has to feel modern but has a taste of retro, cozy, comfy, easy to use"): a shared `theme.rs` (warm amber/sage/terracotta accents layered over the terminal's own default fg/bg, never forcing a background — stays readable on light and dark terminals alike), rounded borders and consistent padding on every panel, and color-coded telemetry status (public/private/disabled). No copy/wording changes beyond what the bug fixes above required — `RULES.md`'s cold/plain/no-slop tone mandate predates this request and is a stronger, earlier-established constraint than a new aesthetic ask implies rewriting text, so the "cozy" treatment is delivered entirely through the visual layer, not through softened language.

### `fossh-admin::data_key` — a genuine concurrency bug, found while re-verifying after an M7 refactor (not part of M7 itself)

Re-running the full workspace suite after starting M7's shared-ingest-logic refactor below, `data_key::tests::concurrent_first_callers_all_converge_on_the_same_key` failed — then passed on retry, which is worse than a clean failure, not better: an intermittently-failing test that gets re-run into a green result is exactly how a real bug hides in plain sight. Isolated it: roughly 2 failures in 5 independent runs, always the same panic (`Corrupt`) from a losing thread's `fs::read` fallback.

Root cause and fix are recorded in full in ADR-0034 — summary: the previous `generate_and_write` had a real window between winning the `create_new` race and finishing `write_all`/`sync_all`, during which a concurrent loser could read a still-empty file and correctly-but-wrongly conclude it was corrupt. Fixed with the standard write-temp-then-atomically-publish pattern (`hard_link`, not `rename` — `rename` replaces rather than fails on an existing destination, which would have let two winners silently disagree on the key instead of one loudly failing). Stress-tested 40 independent runs post-fix, 0 failures, against a measured ~40% failure rate before.

Not a security bug — S2's fail-closed behavior was working exactly as designed, it was just triggering more often than it needed to, only in the narrow window right after a fresh install before `.data_key` exists at all. Recorded here rather than silently folded into the M7 commit since it's a real, independent fix to already-shipped §3.8 code, not new M7 work.

### M7 — FastCGI + optional HTTP listener (original spec, not a prrr.md §3.x sub-chapter)

Not part of the Fedora Native Deployment chapter this file otherwise tracks — M7 is the original `fossh-implementation-prompt.md`'s own milestone 7, picked up because it was the largest genuinely unstarted piece of the base product and this session had the room to do it properly, adversarial review included.

**Built:** a new crate, `crates/fossh-fcgi` — a persistent process speaking FastCGI directly over a Unix socket, for deployments wanting higher throughput than a fresh `fossh-cgi` process per request. Hand-rolled the wire protocol itself (`protocol.rs`: the 8-byte record header, `BEGIN_REQUEST`/`PARAMS`/`STDIN`/`STDOUT`/`END_REQUEST`, the length-prefixed name/value encoding PARAMS and CGI environment variables share) rather than pulling a `fastcgi` crate — same reasoning this project already applies to CRC-32/base32/HLL: small format, security-relevant (untrusted bytes off a socket), worth owning and reviewing directly. `connection.rs` assembles one full request per the canonical BEGIN→PARAMS→STDIN order every real FastCGI client (nginx included) actually sends, mapping PARAMS onto the exact same `fossh_ingest::ingest::IngestEnv` shape `fossh-cgi` already builds from real CGI env vars. `writer.rs` is a single dedicated thread owning the one `Store` handle this process ever touches, batching accepted events every 100 events or 500ms into one shared transaction per flush (`fossh_store::Store::record_events_batch`, new) instead of committing per-event.

**Refactored ahead of building it:** extracted the auth/rate-limit/pipeline-dispatch logic `fossh-cgi::handler` used to inline directly into `fossh_ingest::ingest::decide()`, so both transports share the actual security-critical path instead of `fossh-fcgi` duplicating it. `fossh-cgi`'s own behavior is unchanged (its test suite proves this — the auth/ratelimit/routing scenarios it used to test directly moved with the logic into `fossh_ingest::ingest`'s own tests, which didn't exist before). Also moved `forwarded.rs` (X-Forwarded-For trust) from `fossh-cgi` to `fossh_ingest`, since `fossh-fcgi` needed the identical logic.

**A real, independent concurrency bug found and fixed along the way, not part of M7 itself:** `fossh-admin::data_key`'s own concurrent-first-caller race — see the entry directly above this one.

**Adversarial review — a genuine, from-scratch protocol/concurrency review, not a rubber stamp.** Five real findings, all fixed and re-verified; two considered and deliberately left as documented, accepted tradeoffs rather than silently skipped. Full detail and reasoning: `DECISIONS.md` ADR-0036. Summary:

1. **High severity, fixed:** no read/write timeout anywhere on an accepted connection — a handful of connections that connect and send nothing permanently wedged the worker that picked each one up (the blocking reads in `connection::read_request` never return on their own), and with the default 8-worker pool, as few as 8 such connections exhausted it, permanently, for the rest of the daemon's life. Fixed with a 30-second timeout in both directions, set before a connection ever reaches a worker.
2. **Low severity, fixed:** the PARAMS accumulator checked its size bound *after* appending, unlike STDIN right below it, which already checked before — bounded either way by one record's own 65535-byte wire cap, but a real, worth-fixing inconsistency. Writing the regression test surfaced a second bug in the *test itself*: a filler sized at exactly `MAX_PARAMS_BYTES` silently wrapped to a wire record length of `0` when cast to the format's own `u16` field, turning an intended "one big record" into an accidental empty end-of-stream marker — caught because the test failed with the wrong error, fixed by capping the test's filler at the real per-record ceiling (`u16::MAX`) instead.
3. **Moderate severity, fixed:** a real, empirically-measured window where the socket file existed at `0755`, not `0600`, between `bind()` and a follow-up `chmod()` — this project already had the *correct* pattern for exactly this problem, in `fossh_store::Store::open` for `fossh.db`, and the socket-bind code just hadn't been written the same way. Fixed with a restrictive process umask held only across the `bind()` call. Verification for this one is deliberately *not* an automated `#[test]` — see the code comment at `manual_check_bind_with_correct_permissions_is_0600_and_restores_umask` in `crates/fossh-fcgi/src/main.rs` for why: writing it as a normal test first caused a real, reproducible intermittent failure in a *different*, unrelated test whenever `cargo test`'s default concurrent execution happened to overlap the two, because `umask` is real process-global state. Verified by hand instead, with a real, working, empirically-confirmed repro (run once with `--test-threads=1` against a temporarily-restored `#[test]` attribute, then reverted) — this project doesn't otherwise need a test-serialization dependency for one narrow case.
4. **Low severity, fixed:** stale-socket removal didn't check whether the socket was actually stale before removing it — a second accidentally-started instance would have silently hijacked a live one's socket, with no warning printed anywhere. Fixed: a real connect attempt first; only a connect failure is treated as safe to remove and rebind.
5. **Considered, left as a documented accepted risk:** both `mpsc` channels (connections, accepted events) are unbounded. Not fixed this pass — bounding them trades one failure mode for another that deserves its own deliberate design rather than being bolted on, and finding #1 above substantially defuses the worst compounding case the review named (wedged workers plus an unbounded events channel), since workers can no longer wedge forever.
6. **Considered, left as a documented, deliberate choice:** oversized PARAMS gets a raw connection close with no response, while oversized STDIN gets a proper 413 — a real asymmetry, but PARAMS content in real deployments is essentially always webserver-generated (nginx sets it, not the visitor), so hitting this path in practice means misconfiguration or an actual probe, not legitimate traffic. Judged not worth the added complexity.

Also confirmed correct by the same review, via real constructed repros rather than trusting the code as written: the `SAVEPOINT`-per-event rollback in `fossh_store::record_events_batch` genuinely undoes real partial writes under a mid-function failure (not just an already-failed no-op — the existing test only exercised the latter); `keep_conn`'s two-requests-on-one-connection lifecycle; and the worker pool's mutex being held only across `.recv()`, never across an actual request being handled.

**Verified against the actual compiled binary, not just `cargo test`:** a real `fossh site create` against a scratch data directory, a real `fossh-fcgi` process started with a real `fossh.toml` and bound to a real Unix socket path, a hand-rolled Python FastCGI client (deliberately independent of this crate's own protocol code) sending a real healthz request (204), a real unauthenticated ingest request (401), and a real authenticated one (204) — then reading the resulting `fossh.db` directly with Python's own `sqlite3` module and confirming exactly one row landed with the correct site, timestamp, and hashed visitor.

**Packaging:** `packaging/systemd/fossh-fcgi.service` (own hardening directives matching `fossh-fcgiwrap.service`'s, `PrivateNetwork=yes` included — this process's own network footprint, like `fossh-cgi`'s, is exactly zero); added to `packaging/rpm/fossh.spec` (binary, service unit, `%post`/`%preun`/`%postun` scriptlets alongside the existing CGI-mode ones — both transports ship enabled but not started, per the same "no enrolled key yet" reasoning already governing `fossh-fcgiwrap.socket`). Rebuilt the actual RPM after these changes (`rpmbuild -bb`, real, not `rpmspec --parse`) and confirmed via `rpm -qlp`/`rpm2cpio`+`file`+`strings`: `fossh-fcgi` is present, stripped, and free of leaked build paths, same as the other three binaries.

**Honest, open gap, not silently glossed over:** `fossh-fcgi` has no SELinux domain of its own. `packaging/selinux/fossh.te`'s existing `fossh_cgi_t` grants deliberately never covered the SQLite database at all (`fossh-cgi` "never opens the actual SQLite database itself" — see that file's own comment) since `fossh-cgi` genuinely doesn't touch it; `fossh-fcgi`'s entire design is the opposite; it opens `fossh.db` directly on every batch flush. With no `type_transition` targeting `/usr/bin/fossh-fcgi`, it runs in whatever domain execs it — typically `unconfined_service_t` on Fedora's targeted policy for a unit with no `SELinuxContext=` of its own — which is functional, not broken, but without the same kernel-enforced confinement `fossh-cgi` has. A real SELinux domain for direct-SQLite access (needing `lock` on the database file, unlike the spool-only path — SQLite's own concurrency control uses POSIX advisory locking) is real, separate follow-up work, not done this pass; noted in `packaging/systemd/fossh-fcgi.service`'s own header comment too, not just here.

**Not done, and explicitly out of scope this pass (ADR-0035):** a spool-mode alternative for `fossh-fcgi` (it only ever writes direct-to-SQLite, per §7.2's own framing of that as what FastCGI mode *is*, not a configurable choice); systemd socket activation (binds its own socket path directly instead); the optional loopback/Unix-socket-only HTTP listener (`feature = "http"`) M7 also names — `fossh_core::config::Config` already has the `[listener]`/`ListenerConfig`/S7-validation groundwork for it (built ahead of this session, confirmed still passing its own tests), but no listener code was written against it this pass.

### §3.3 — OCaml watchdog, first slice (logic layer: supervision, auth-gate primitives, tamper detection)

First OCaml code in this project. This is the one sub-chapter in this chapter that ran the full mandated QA gate (sandbox → implement → stop → adversarial subagent → fix → retrospective → this table) in the intended order, on the first pass, rather than being caught retroactively like §3.9 above. The adversarial review found 10 real, independently-reproduced findings — full detail in ADR-0041, not repeated here — two of them critical: the initial process spawn bypassed the tamper check entirely (only restarts went through it), and a validly-signed manifest that never mentioned the program actually being executed passed trivially, meaning the tamper-detection guarantee this whole component exists to provide wasn't actually bound to what got run, in two independent ways. All 10 fixed and re-verified against the real compiled binary in the same pass — none deferred, except one (constant-time session-token comparison) that's genuinely unreachable until §3.4 wires up a network listener, which is documented as the reason, not silence.
